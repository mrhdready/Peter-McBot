# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is the contributor guide (structure, style, test and security rules) and applies here too. This file adds the context that takes several files to piece together. The README and `docs/` are in German; `docs/ARCHITEKTUR.md` covers the HTTP API, and `docs/KARTE.md` covers the persistent map.

## What this is

A Minecraft **Bedrock** AFK bot with a local web control panel. It is a single Node.js 24 process, written in strict TypeScript, that connects to an existing server over HTTP-NetherNet (pure-JS WebRTC via `werift`) using an offline identity. It has been verified only against Bedrock 1.26.65 / protocol 2225, with data version `1.26.60`. Other protocol numbers are rejected.

## Commands

Use Node.js 24 (`engines: >=24 <25`) and pnpm 11.25.0.

```sh
pnpm install --frozen-lockfile    # applies patches/ via pnpm-workspace.yaml; install scripts are disabled
pnpm build                        # tsc: src/ -> dist/, then copies src/ui -> dist/ui
pnpm test                         # pnpm build && node --test test/*.test.cjs
pnpm build && node --test test/web.test.cjs                         # one test file
pnpm build && node --test --test-name-pattern "SSE" test/web.test.cjs  # one test by name
node --env-file=.env dist/main.js # run locally; `pnpm start` does NOT load .env
pnpm check:compatibility          # offline; writes ignored compatibility-result.json
```

No linter or formatter is configured; `tsc` is the only static check.

**Tests are CommonJS (`.cjs`) and `require('../dist/...')`**, so they run against compiled output. Always rebuild before running a single test file, or you will be testing stale code.

`scripts/probe-server.cjs` and `scripts/smoke-*.cjs` connect to a **real server**, and the movement smoke tests move a real player. Run them only when the user explicitly asks, with `node --env-file=.env --env-file=config/smoke.env scripts/<name>.cjs`.

## Architecture

**Wiring (`main.ts`).** `main.ts` builds a `BotController` with an injected `ClientFactory` that wraps `bedrock-protocol`'s `createClient`, then creates a `MapArchive` and connects it via `bot.state.onSurfaceTile`. It also starts `createWebServer(bot, archive)` and flushes the archive every 5 s and on SIGINT/SIGTERM. The bot never connects automatically at startup; a `connect` command is required. Tests inject a fake `EventEmitter` client and a controllable `now()` instead of a real connection (see `test/bot.test.cjs`).

**Single-threaded command loop (`bot.ts`).** HTTP handlers never touch the bot directly; they call `bot.enqueue(command)`. The queue holds at most 32 commands, and `stop_navigation` jumps the queue. A 50 ms `setInterval` (`step()`, the 20-Hz heartbeat) drains the queue and handles connection state: wanted/connecting, the login timeout and bounded retry. It also advances navigation and time-sliced preview jobs, and flushes surface changes. Any new long-running work should be a step-able job driven by this tick, not a separate timer.

**World model (`state.ts`, `world.ts`, `chunk-worker.ts`).** `WorldState` owns position, dimension, status and the chunk cache: a circular radius of 4–6 chunks, set by `CHUNK_RADIUS`. Chunk decoding runs in a `worker_threads` Worker loaded from `dist/chunk-worker.js`. Missing columns and subchunks are requested explicitly, with limited retries spread out over time. **Unknown data is never treated as air.** Known and unknown must stay distinguishable everywhere: pathfinding, map rendering and block search. `WorldState.players` holds other players in the server's entity range (from `add_player`, moved by `move_player`/`move_entity_delta`, dropped by `remove_entity` (which carries the unique ID, not the runtime ID), a `player_list` removal (by UUID) and `resetWorld`). It is kept in memory only and exposed as `players` in the snapshot; the UI shows each as a `pin-player` chip with an animal emoji hashed from the gamertag. `WorldState.roster` (UUID → name) holds everyone on the server from `player_list` add/remove records, minus the bot (matched by `start_game.entity_id` or `BOT_NAME`); it is cleared by `resetWorld` and exposed as `roster: [{name, position}]`, where `position` comes from the `players` entry with the same UUID or is `null`. The sidebar's "Spieler" panel lists it.

**Movement (`pathfinder.ts`, `terrain.ts`, `navigation.ts`).**
- `pathfinder.ts` is the one shared incremental A* used by both preview and navigation. Its limits: 16384 nodes, ≤128 nodes per call, a ~4 ms soft budget per call, and a 15 s cap on previews. It optimises for safe handling, not distance: weighted step costs (`COST_*`: flat 1, slab/stair 1.5, drop 4, jump 5, +2 next to a drop/hole/unknown via `Terrain.dropHazard`). Every cost is ≥1, so the Manhattan heuristic stays admissible.
- `navigation.ts` classifies each waypoint as `pass` (straight, level, no `dropHazard` in the 8 surrounding columns, next waypoint standable), `corner` (level turn on safe ground, reached within 0.2) or `stop` (reached within 0.08). Safe level segments use vanilla walking speed (`WALK_SPEED` ≈ 0.216 blocks/tick, full input) with a look-ahead braking profile; segments with a height change, next to an edge or airborne keep the original careful speed (0.06, input ≤ 0.3). `terrain.move` accepts at most `MAX_HORIZONTAL_STEP` (0.3) per tick.
- **Doors (`OPEN_DOORS`, default on → `WorldState.openDoors`).** minecraft-data 1.26.60 gives every door state the same west-side panel, so the chunk worker replaces door collision with the vanilla 3/16 panel derived from `minecraft:cardinal_direction` (a quarter turn off for doors: "south" is a vanilla east-facing door, verified live), `open_bit` and `door_hinge_bit` (fence gate shapes in the data are correct). Bedrock keeps facing and open state on the lower door half only, so `world.ts` resolves upper halves to the lower half for collision, `doorAt` and `closedDoorAt`. It also pairs closed/open states (`open_bit`) of every `*_door` except `iron_door` and every `*fence_gate`. `RoutePlanner` plans on `world.planningTerrain`, which reads closed openable doors as open (except those in `world.blockedDoors`) and adds `COST_DOOR` (3). Tests that replace `state.terrain` must replace `state.planningTerrain` too. `navigation.ts` stops at the waypoint before a step that is blocked only by a closed door, sends one `inventory_transaction` (`item_use`/`click_block`, empty hand, hotbar slot 0), waits up to 2 s for `update_block`, then marks both halves blocked for this navigation and replans. It closes doors it opened once its box has left the door block, unless another player is within 2 blocks or the door is more than 4 blocks away.
- `navigation.ts` accepts small on-path server corrections without replanning, fails only after more than 3 replans *without waypoint progress*, and waits up to 3 s at an unknown waypoint before replanning. Decisions are logged with the `[nav]` prefix.
- `terrain.ts` answers collision, headroom and landing questions. It handles full blocks, slabs and direction-dependent stairs; farmland and `grass_path` (15/16 high) are support too (set in `chunk-worker.ts`), crops have no collision; route nodes keep feet heights at 1/16-block precision. Steps can go at most 1 block up or 1 block down.
- `navigation.ts` turns a plan into protocol input packets.
- **Preview isolation is a hard invariant:** `/api/preview` must not change position or active navigation, and must not send movement packets. Tests cover this.

**Persistent map (`map-archive.ts`).** Observed *surfaces* (not full chunks) are stored as 16×16 tiles under `data/maps/`. They are keyed by normalized host/port/transport + `MAP_WORLD_ID` + dimension. Writes go to a temp file and are then atomically renamed. Historical tiles are for display only: navigation, preview and block search use **only** the live cache. Merge rules: an incomplete observation never replaces a confirmed surface, while fully known air may replace old blocks. The tile and manifest endpoints use SHA-256 fingerprints and ETags to return 304.

**Web (`web.ts`, `src/ui/`).** `web.ts` holds the `node:http` routes and SSE. The UI lives in `src/ui/index.html`, `style.css` and `app.js`: a map-centred layout with a sidebar, and below 900px a fixed navigation bar. `pnpm build` copies `src/ui` to `dist/ui`; `web.ts` reads the files once at startup and inlines the style and script into the placeholders `<!-- ui:style -->` and `<!-- ui:script -->`. There is no frontend framework or bundler. Tests extract the **single** inline `<script>` and run it against a fake DOM that offers only `getElementById` and `createElement`, so `app.js` must not use `querySelector`, `classList` or other DOM APIs beyond plain property assignment (including `element.style.*`, which the fake elements support). Keep the existing element IDs, because tests address them. Sidebar panels other than "Ziel & Navigation" are native `<details class="panel">` with the `h2` inside `<summary>` (no JS); "Ziel & Navigation" must stay a `<section>` because it contains `#navigate`, the fixed bottom bar below 900px. POSTs require `Content-Type: application/json` and reject foreign `Origin` headers. This is not authentication: the UI is meant for a trusted network only. `createWebServer(bot)` without an archive falls back to the legacy unpersisted `/api/map`.

**Skin (`skin.ts`).** `SkinStore` keeps one custom skin in `data/skin.json` (model and the normalised 64×64 PNG; 64×32 uploads are expanded like Java's legacy conversion). PNGs are decoded with `pngjs`, and the IHDR size is checked before decoding. The skin is sent only in the login chain: the client factory in `main.ts` spreads `skins.connectSkinData()` into `skinData` at every connect, which overrides bedrock-protocol's default persona skin with a classic skin on `geometry.humanoid.custom`/`customSlim`. An upload therefore applies on the next connect. `createWebServer(bot, archive, places, skins)` serves `GET /api/skin`, `POST /api/skin` and `POST /api/skin/delete`, and adds `skin: {saved, model, active, error}` to the SSE snapshot; the UI offers a reconnect when `saved !== active`. An unreadable file is reported and the bot connects with the default skin.

**Chat commands (`chat-commands.ts`).** `bot.ts` passes `text` packets of type `chat`/`whisper` from other players to `bot.onChat` and sends public chat with `bot.say` (an `authored`/`chat` text packet). `main.ts` wires `ChatCommands(bot, places, radius * 16, BOT_NAME)` unless `CHAT_COMMANDS=off`. A line is a command when it starts with the bot name (case-insensitive, optional `@`, optional `,`/`:`). Commands: `hallo|hi|hey`, `go <place>` (exact, then unique-prefix POI name in the current dimension), `come` (to ~2 blocks short of the visible sender), `find <block>` (nearest hit from the sender if visible, else from the bot; `limit` 1), `inventory|inv`, `give <item> [n]` (see Inventory), `put <item>|all [n]` and `get <item> [n]` (see Chests), `stop` (also ends a put/get run), anything else → help. Targets beyond the loaded radius are refused; there is a 2 s cooldown per sender. `BotController` also keeps a read-only chat log for the UI: the last 100 lines (player chat, whispers, `say` replies, and `event` marks on spawn and on losing a spawned connection), with §-codes stripped, in memory only. It is served by `GET /api/chat` and announced via `chatRevision` in the SSE snapshot. The UI's `#chat-panel` is a sidebar `<details>`; from 1400px CSS turns it into an absolutely positioned left column of `.layout`, and the script opens it except below 900px. Navigations carry an optional `origin` in the `navigate` command; `bot.onNavigationEnd(origin, status, message)` fires once per run (arrived, error, stopped, replaced by a new target, or reset on disconnect), and only chat-origin runs are announced. Logs use the `[chat]` prefix.

**Inventory (`inventory.ts`).** `WorldState.inventory` holds the bot's 36 slots (hotbar 0–8, main 9–35) from `inventory_content`/`inventory_slot` of window `inventory` only, plus pickups, which BDS reports as a clientbound `inventory_transaction` whose `container` action (window 0) carries the slot's `new_item`; names from `item_registry` (unknown IDs show as `#<id>`); memory only, cleared by `resetWorld`. Bedrock inventories are server-authoritative: `bot.dropItems(name, count, toward)` queues a job that the next tick runs as `navigator.face` (one zero-input `player_auth_input` with the yaw towards the receiver) plus one `item_stack_request` with a `drop` action per stack (container `hotbar`/`inventory`, the server's stack ID, negative odd request IDs). Counts change only from the `item_stack_response` (status `ok`); rejection, 3 s without answer or a disconnect reject the promise. Exposed as `GET /api/inventory` and `inventoryRevision` in the SSE snapshot; the UI panel is read-only. Chat `give` resolves the item like `go` (exact short/full name, then unique prefix), walks up like `come` with a `give` token in the navigation origin, and on arrival throws only if the sender is within 4 blocks; it replies after the server's confirmation. Logs use `[inv]`. Drop and pickup are verified live with `scripts/smoke-inventory.cjs` (`SMOKE_WATCH=<s>` records the packets of a pickup).

**Chests (`bot.ts` `useChest`, `inventory.ts`, `chat-commands.ts`).** Protocol facts verified live with `scripts/smoke-chest.cjs`: the click is the door-style `inventory_transaction` (`navigator.clickBlock`, hotbar slot 0 with its raw item), and **the server handles it only together with a following `player_auth_input`**, so the job sends `navigator.face` every tick until `container_open` (≤2 s). A chest opens as window_type `container`; a double chest is one window of 54 slots; its content is an `inventory_content` with the same window ID, and the server then resends the bot's inventory with **new stack IDs** (the job waits 100 ms before the first move). Stack requests name the chest's slots `container` (`level_entity` is rejected with status 50); a single `place` action moves items directly in both directions. `bot.useChest(chest, planner)` is a tick-driven job (click → opening → content → move → close) that asks the planner for one move at a time, after each `item_stack_response`, so stack IDs and counts are always the server's; `Inventory.window` (`ContainerWindow`) mirrors the open chest. `inventory.nextTransfer` plans a move (source slots in slot order; partial stacks up to `stackSize` from prismarine-registry first, then empty slots). A `navigate` command, `stop_navigation` or a server close ends the job (a running request is awaited, then `container_close`); a disconnect rejects it. Chat `put`/`get` search `CHEST_IDS` (`chest`, `trapped_chest`, all `copper_chest` variants) from the bot within the loaded radius with `searchBlocks(list)`, open chests within 4.5 blocks of the eyes directly and walk to a free neighbour column for others (`chest` token in the navigation origin, no arrival line), try at most 5 opened and 10 candidate chests, drop the other half of a 54-slot chest, announce a full chest (put) or a missing item (get with a count) before moving on, and end with one summary. `get` resolves the item name against each chest's content. Nothing about chest contents is stored. Logs use `[chest]`.

**Farming (`farming.ts`).** `Farmer` belongs to the bot (`bot.farm`, created in its constructor with a `FarmHost` of getters and closures), so the web UI can switch it without chat commands. A round is an async loop that only the tick advances: `bot.step()` calls `farm.step(send)` in the spawned branch, and every wait (`ticks`, `act`, `external` for search and chest promises, `walk` for navigations with a `farm` token in the origin) is a promise that `step` resolves; a new token per run (off, `pause`, `disconnected`) rejects the running wait. `settleNavigation` and the replace path route `farm` origins to `farm.navigationEnded` instead of `onNavigationEnd`. A round: walk to the anchor if more than the radius (24, capped to loaded radius − 1 chunk) away, `world.ripeCrops` (growth 7 of `CROP_KINDS`, horizontal radius), then cluster by cluster (`standFor`: within the 3×3 around the nearest target, the standable column reaching most targets at Chebyshev ≤ 1): break each crop with the live-verified recipe (`navigator.lookAt` with flag `block_action`, tick 1 `[start_break, predict_break]`, tick 2 `[stop_break]`), walk onto drop columns (`WorldState.items` from `add_item_entity`/`take_item_entity`/`remove_entity`), replant (seed to the hotbar via `inventory.place`, `mob_equipment`, **an `abort_break` tick first**, then `clickBlock` with face 1 and the hotbar slot; success = the crop appears within 2 s and still stands 500 ms later). Spots without seed are kept in memory, one chest `get` per round is tried, then reported once. Surplus above `RESERVE` goes to the nearest chest via `bot.useChest` (`chestStandSpot` from `chat-commands.ts`). Chat `go/come/give/put/get` call `farm.pause()` (60 s after the last); a UI `navigate` and `stop_navigation` call `farm.off`. Chat `farming on|once [place]|off` and `farming` (status); `farm.onReport` is wired to chat by `ChatCommands`. `POST /api/farm` and `farm` in the SSE snapshot; UI panel `#farm-panel`. Logs use `[farm]`. `scripts/smoke-farm.cjs` verified the protocol; `SMOKE_MODE=feature` runs one real `farming once` round.

**3D viewer (`viewer-mapping.ts`, `viewer-stream.ts`, `viewer-worker.ts`, `viewer-assets.ts`, `src/ui/viewer.js`).** Details in `docs/viewer.md`. A Socket.IO feed on `/api/viewer/socket` streams live columns converted in a worker from the Bedrock palette to Java **1.21.11** (`blocksB2J` plus `VIEWER_OVERRIDES`; Bedrock-only variants take the closest entry of the same block, `viewerAlias` draws poplar as birch; chests forced to `type=single`) for the patched `prismarine-viewer` mesher in the browser. `/viewer/atlas.png` and `/viewer/blocksStates.json` come from `ViewerAssets`: with `MINECRAFT_EULA=true`, `main.ts` downloads the pinned 1.21.11 client jar (SHA-1 and size from Mojang's manifest) into `data/viewer-assets/1.21.11/` and builds atlas and block states from it (own zip reader, `pngjs`, box models for chests/beds/shulkers); `meta.json` marks a complete cache. Otherwise the bundled 1.21.4 assets are served. The worker logs `[viewer]` diagnostics (`no-translation`, `no-java-block`, `no-model`) once per state and viewer session. Each volatile `position` packet also carries `self`/`players` (bot name/sleep flag from `createViewerStream`'s `self` getter, `WorldState.players` with yaw/pitch); `viewer.js` draws them as placeholder figures (bot hidden in bot view). Phase plan for mobs, items, models and a first-person hand: `docs/viewer-entities.md`.

**Map performance (`map-performance.ts`).** This module provides `/?measure=1` and `/api/map-performance`, which report Node and cgroup counters.

**Places (`places.ts`).** `PlaceStore` keeps saved places (POIs) and the last 10 accepted navigation targets per dimension in one JSON file per server/world under `data/places/`, keyed like the map archive. Every operation runs exclusively and commits in memory only after the atomic write succeeds; an unreadable file is reported and never overwritten. `createWebServer(bot, archive, places)` serves `GET /api/pois?dimension=N`, `POST /api/pois` and `POST /api/pois/delete`, records each accepted `/api/navigate`, and adds `placesRevision` to the SSE snapshot so clients refetch. Without a store the UI panel is hidden (`placesEnabled`). In the UI, bot (🤖), target (📌), places (📍) and block-search hits (⛏️, one pin per X/Z column; `#search-reset` clears them) are DOM pins in `#map-pins` with `pointer-events: none`; the canvas hit-tests them in screen pixels, so dragging and zooming stay on the canvas.

## Dependency patches and trust

`bedrock-protocol@3.61.0` and `prismarine-chunk@1.41.0` are pinned exactly and patched through `patches/`, listed in `pnpm-workspace.yaml`. The patches add NetherNet signalling, signed offline identity, the Bedrock 1.26 chunk loader and the runtime-ID hash fix. Changing those versions means regenerating the patches and keeping the lockfile consistent.

The server operator key is pinned in `data/server-key.sha256`. Do not weaken signature, DTLS or key-pin checks, and never "fix" compatibility by downgrading the server or world.

## Deployment

- `.github/workflows/docker-build.yml` builds the Dockerfile on every push and PR. It publishes to GHCR only on a push to `main`.
- `compose.yaml` pulls `BOT_IMAGE` from `.env`; it has no local build.
- `pnpm prepare:arcane` reads `config/arcane.env` and generates the ignored `deploy/arcane/` from `deploy/arcane-template/`. Edit the template, not the output.
- `test/deployment.test.cjs` checks the deployment configuration.
