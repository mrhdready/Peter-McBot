# Live 3D view

Select **3D** above the map. The map remains the default. **Frei** uses mouse dragging to look, WASD to move horizontally, and Q/E to descend/ascend. Focus the canvas before using the keyboard. **Bot-Sicht** follows the bot's eye position and reported/sent orientation. **Zum Bot** returns the free camera to the bot. Camera controls never send movement commands to Minecraft.

The compact **Invertieren: X / Y** switches beside **Zum Bot** independently reverse mouse dragging in the free camera. Both switches default to off; the horizontal base direction is reversed in the camera controls themselves. Both choices are saved in this browser's local storage and restored after reloading; stored choices override the defaults. If storage is blocked, the switches still work for the current page. They do not change the bot's orientation. Bot-view position and look are smoothed between network updates using frame-rate-independent damping (60 ms time constant). Yaw takes the shortest turn across the ±180° boundary. Mode switches and position jumps exceeding eight blocks snap to the bot instead of flying through intervening terrain.

The backend remains headless. WebGL is required only in the browser. Loading or rendering failures return to the map. Route overlays and destination selection remain outside the 3D view; use the map for navigation and markers.

## Bot and players

The bot and other players in the server's entity range appear as placeholder figures: a body box and a head with a light face marker on the side they look at, plus a name tag. The bot is blue with 🤖; each player gets a colour hashed from the gamertag and the same animal emoji as on the map. The bot is shown only in **Frei**, not in **Bot-Sicht**, and lies down while it sleeps. Figures are damped like the bot view; jumps over eight blocks snap. Look directions come from `add_player`, `move_player` and `move_entity_delta` (`rot_x`/`rot_y` as byte angles, 256 per turn).

## Animals and mobs

Mobs, boats and minecarts within the live radius appear as boxes the size of their hitbox: nearest first, at most 128. The size comes from the server's bounding-box metadata, then from minecraft-data, and otherwise falls back to 0.8 blocks; the server's `scale` metadata applies on top, because babies report the adult box (without a scale, babies are halved). Passive mobs are green, hostile mobs red and everything else grey. A head cube at the top front edge turns by the head yaw. Only mobs with a custom name carry a name tag; hovering over a mob in the free camera shows its type. Projectiles, XP orbs, leash knots, frames and paintings are not drawn. The server tracks them in `WorldState.entities` (`src/entities.ts`) and resolves the look; the viewer only draws it. Dropped items and real models are not shown yet; see `docs/viewer-entities.md` for the phases.

## Data and limits

The viewer uses the existing circular `CHUNK_RADIUS` cache (4–6 chunks) in the bot's current dimension. Free camera movement does not request extra chunks. Map zoom and historical surface tiles are independent: archived surfaces cannot reconstruct buildings or caves. Missing sections render without geometry; the status reports how many sections are known. Confirmed air remains distinct from unknown sections in the bot's world model.

`ViewerMapping` converts the Bedrock palette through the installed `minecraft-data` `blocksB2J` table to Java **1.21.11**, the version that table targets. This does not change the Bedrock server version. Additional stair-corner states and second-layer water are handled explicitly. The table only lists Bedrock states that some Java state maps to, so Bedrock-only variants of a listed block (for example a pumpkin's facing or bamboo `age_bit=1`) use the entry of the same block that agrees on the most properties. Bedrock-only blocks without a Java counterpart are drawn as a similar block via `viewerAlias`: poplar wood becomes birch, and the red, orange and yellow poplar leaves become green birch leaves. Bedrock keeps chest pairing in block entity data, so all chests are drawn as single chests. Non-air secondary layers without a Java waterlogged equivalent cannot be represented independently. Unknown blocks and unrepresentable states become magenta wool. `VIEWER_OVERRIDES` in `src/viewer-mapping.ts` adds hand-maintained translations (Bedrock name or canonical state → Java state) and takes precedence over the table. Java textures, default biome tinting (1.16.2 tint table plus fixed colours for mangrove leaves and leaf litter) and simplified lighting are used. Bedrock resource packs are not loaded.

## Textures and Mojang assets

Without further configuration the viewer uses the 1.21.4 atlas and block states shipped with `prismarine-viewer`. They are keyed by block name, so they work with the 1.21.11 palette; blocks newer than 1.21.4 show the upstream missing-texture cube, and block entities (chests, beds, shulker boxes) have no geometry.

`MINECRAFT_EULA=true` accepts the [Minecraft EULA](https://www.minecraft.net/eula), like `EULA=true` for the dedicated server. At startup the bot then downloads the Java **1.21.11** client jar once in the background from Mojang's content-addressed URL, checks the pinned size and SHA-1 from the version manifest, and builds the atlas and block states into `data/viewer-assets/1.21.11/` (`client.jar`, `atlas.png`, `blocksStates.json[.gz]`, `meta.json`, written last). The bot connects independently; a failed download or build is logged once per start and the fallback stays active. Hosts without internet access can place the matching `client.jar` in that folder. Nothing from the jar is part of the repository or the Docker image. A finished cache is used from the next 3D view or page reload on; it is also used when `MINECRAFT_EULA` is later unset. Raising `GENERATOR_VERSION` in `src/viewer-assets.ts` rebuilds the cache from the kept jar.

The generator (`src/viewer-assets.ts`) reads the jar with a small zip reader (stored/deflate only, size limits, no file paths derived from entry names) and decodes textures with `pngjs`. It flattens model parents, resolves texture references and bakes UVs into 16-px atlas tiles in the format the `prismarine-viewer` mesher expects. Animated textures use their first frame. Missing models or textures use a magenta/black checker tile and are listed in the startup log. Chests (including trapped, ender and copper chests), beds and shulker boxes get approximate box models cut from their entity textures, not pixel-exact copies of the entity renderers. Signs, banners, heads and other block entities remain without geometry.

## Diagnosis

The conversion worker logs with the `[viewer]` prefix: one summary when the first 3D viewer starts (`palette java 1.21.11, assets mojang|fallback, N bedrock states unmapped, M without model`) and, once per viewer session, one line per Bedrock state that is drawn as a fallback: `[viewer] unmapped <name>[<states>] reason=<reason> at x,y,z`. `no-translation` means the table has no entry, `no-java-block` that the translated Java state does not exist in 1.21.11, and `no-model` that the active assets have no model for the Java block. These lines are the input for `VIEWER_OVERRIDES`.

Palette creation and chunk conversion run in a dedicated Node worker. A Socket.IO feed on `/api/viewer/socket` sends session resets, position/look updates at up to 10 Hz (each also carrying the bot name and sleep flag, the players with viewer-space pose and the drawn mobs), column loads/replacements and unloads. Block changes replace affected columns; there is no per-block delta protocol. Converted columns are cached by immutable section references. One column per client awaits acknowledgement, with a 15-second timeout; at most four 3D clients connect. Slow clients cannot create an unbounded chunk queue. Switching back closes the socket and disposes the rendering loop, mesh workers and WebGL resources. The conversion worker stops when the last viewer disconnects.

## Build and deployment

`pnpm build` compiles TypeScript, copies the existing UI and runs `scripts/build-viewer.cjs`. It bundles the viewer and mesher with only the required Java 1.21.11 palette, copies the 1.21.4 fallback atlas/block states, and generates gzip variants. `/viewer/atlas.png` and `/viewer/blocksStates.json` resolve to the Mojang cache when it is complete, otherwise to the fallback. All assets are served locally from an explicit `/viewer/` allowlist. There is no CDN or separate listening port. Docker runs the same build. Dependency lifecycle scripts remain disabled.

The maintained pnpm patch fixes the published viewer's negative-height loops, section indexing and bottom-face culling for Y **-64 through 319**, uses local asset paths, disposes reset meshes, and rejects meshing responses from previous world generations. It also adds 1.21.11 to the supported versions (otherwise `getVersion` would fall back to 1.21.4 and mismatch the palette), reads the newer `material` format (`plant;mineable/axe`) for liquid culling and adds the fixed tints mentioned above. Keep this patch when updating dependencies. A version upgrade must keep the mapping palette, block assets, browser worker and height handling aligned.

## Verification

`pnpm test` includes palette validity, stairs/water/fallbacks, the diagnosis, height extremes, camera axes, the actual bundled mesher, HTTP assets and socket updates/evictions/session resets. `test/viewer-assets.test.cjs` checks the zip reader, generator, cache and routes against a synthetic mini-jar; the real Mojang jar is only verified live. Browser verification with synthetic chunks must be distinguished from live-server evidence. A browser without WebGL can verify the map fallback but cannot validate the rendered scene or GPU performance.
